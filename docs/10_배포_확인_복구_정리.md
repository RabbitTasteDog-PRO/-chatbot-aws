# 배포 확인·복구·리소스 정리

## 1. 실행 중인 이미지와 데이터 확인

**새 EC2 터미널**의 운영 폴더에서 실행. 실제 `.env` 내용은 화면에 출력하지 않음.

```bash
cd /home/ubuntu/chatbot-aws
sudo docker compose --env-file .env --env-file deploy/release.env -f compose.prod.yaml ps -a
cat deploy/release.env
```

**확인 결과:** `backend`는 healthy, `gateway`는 실행 중이고 `80:80` 연결이 보임. `frontend`·`db` 컨테이너는 운영 서버에서 실행하지 않음. `release.env`는 마지막 백엔드 성공 이미지의 기록이며 현재 컨테이너 상태는 `ps`와 함께 확인.

**내 PC 브라우저**에서 CloudFront 주소 또는 연결한 서비스 도메인을 열어 아래 순서 확인.

1. 회원가입·로그인 후 질문 한 개 전송.
2. 새로고침해 같은 대화가 남아 있는지 확인.
3. **대화 내보내기 → TXT 다운로드**로 S3 저장 후 파일 다운로드.
4. **S3 → 기존 대화 버킷 → 객체 → day2/chat-exports/**에서 생성 파일 확인. 프론트 버킷에서 찾지 않음.
5. 브라우저의 로그아웃 후 보호된 대화에 접근할 수 없는지 확인.

백엔드 컨테이너를 재생성해도 데이터는 RDS에 남음. S3 임시 URL은 유효 기간 안에는 받은 사람이 사용할 수 있으므로 다른 사람에게 공유하지 않음. 로그아웃만으로 이미 발급한 URL이 취소되지는 않음.

## 2. 자동 배포 결과 확인

**GitHub → Actions → Deploy React and Django → 최근 성공 실행**에서 테스트·ECR·SSM·S3·CloudFront 검사까지 모두 성공했는지 확인. 마지막 요약의 백엔드 태그와 커밋 기록 확인.

화면 검사에서는 공개 `index.html`이 이번 빌드 파일과 같은지, API 검사에서는 `status`·`database`가 `ok`인지 확인함. 이 자동 검사가 회원가입·채팅·S3 다운로드 전체를 대신하지 않으므로 앞 단계의 기능 확인도 진행.

실패한 코드의 차단을 확인하려면 별도 작업 브랜치에서 테스트를 실패하게 만든 후 PR 생성. **CI가 실패하고 운영 배포는 실행되지 않아야 함.** 실패 코드를 main에 병합하지 않고 해당 실습 PR을 닫기.

## 3. 백엔드 이전 버전으로 복구

**EC2 터미널**에서 기록 확인. 첫 성공 배포만 한 경우 `previous.env`는 아직 없을 수 있음.

```bash
cd /home/ubuntu/chatbot-aws
cat deploy/release.env
cat deploy/previous.env
```

- **새 배포가 실패한 직후:** `release.env`가 마지막 성공 이미지임. 그 태그로 복구.
- **새 배포가 성공했지만 이전 버전으로 돌아갈 때:** `previous.env`의 태그 선택.
- 실패한 배포가 이미 컨테이너를 교체했을 수 있음. 스크립트는 자동으로 이전 컨테이너를 복원하지 않음.

아래 `RESTORE_TAG`를 복구할 이미지의 마지막 `:태그`로 변경. `ORIGIN_HOST`는 현재 CloudFront API 원본의 도메인, `VIEWER_DOMAIN`은 브라우저에서 사용하는 도메인.

```bash
sudo bash deploy/deploy.sh RESTORE_TAG ACCOUNT_ID.dkr.ecr.ap-northeast-2.amazonaws.com skn33-chatbot-backend-ALIAS ORIGIN_HOST https://VIEWER_DOMAIN
```

**확인 결과:** API·DB 검증 성공 후 복구한 태그가 `release.env`에 기록됨. DB 마이그레이션은 되돌리지 않으므로 이전 코드와 현재 스키마가 호환될 때만 진행. 수업의 화면 문구 수정에는 스키마 변경을 포함하지 않음.

## 4. 프론트 이전 버전으로 복구

**내 PC의 프로젝트 폴더**에서 실행. `GOOD_COMMIT`은 GitHub의 성공 실행에 표시된 커밋 SHA. 현재 작업을 덮어쓰지 않고 별도 작업 폴더를 만듦.

```bash
git worktree add --detach ../chatbot-aws-rollback GOOD_COMMIT
cd ../chatbot-aws-rollback/frontend
npm ci
npm run build
cd ..
AWS_PROFILE=skn33 AWS_REGION=ap-northeast-2 bash deploy/frontend.sh FRONTEND_BUCKET DISTRIBUTION_ID frontend/dist
```

**확인 결과:** CloudFront 무효화가 끝난 뒤 이전 화면 표시. 기존 해시 자산은 업로드 스크립트에서 삭제하지 않음. 백엔드만 복구하면 프론트는 바뀌지 않으며 두 버전의 API 호환성도 확인.

## 5. 증상별 확인

| 증상 | 확인 순서 |
| --- | --- |
| React 화면이 안 나옴 | S3 루트의 index.html → CloudFront 기본 원본 S3 → OAC와 버킷 정책 → 기본 루트 객체 |
| API 응답이 HTML임 | /api/* 동작의 API 원본 선택 → 403/404를 index.html로 바꾸는 전역 오류 설정 제거 |
| 로그인·쓰기 403 | API 쿠키·헤더 전달, CachingDisabled, CSRF_TRUSTED_ORIGINS의 실제 HTTPS 주소 |
| Django 400 | 원본 도메인과 DJANGO_ALLOWED_HOSTS 일치 확인. Viewer 도메인과 원본 도메인 구분 |
| RDS 연결 시간 초과 | 사용 가능 상태 → 같은 VPC → 새 EC2 아웃바운드 → RDS 인바운드의 새 EC2 그룹 |
| S3 NoCredentialsError | 새 EC2 IAM 역할 → IMDSv2 응답 홉 제한 2 → 컨테이너 재생성 |
| S3 AccessDenied | S3_EXPORT_BUCKET이 기존 대화 버킷인지, EC2 역할이 day2/chat-exports/*의 PutObject/GetObject를 허용하는지 확인 |
| SSM 배포 대상 없음 | GitHub EC2_INSTANCE_ID → 서울 리전 → SSM Online → 해당 새 인스턴스로 제한한 IAM 정책 |
| ALB 전환 후 502 | origin 도메인 DNS → 서울 인증서 이름 일치 → CloudFront HTTPS 원본 → ALB 대상 Healthy |
| 설정 수정 후 그대로임 | .env 변경 후 같은 이미지로 deploy.sh 재실행. restart만으로 환경 변수가 바뀌지 않음 |

앱 로그는 EC2에서 필요한 서비스만 확인.

```bash
sudo docker compose --env-file .env --env-file deploy/release.env -f compose.prod.yaml logs --tail=80 backend gateway
```

## 6. 다음에 이어서 사용할 때

EC2와 RDS는 각각 중지. S3·CloudFront·ALB에는 EC2와 같은 중지 기능이 없음. EC2 중지 중에도 EBS·보유한 공인 IPv4, RDS 중지 중에도 저장 공간·보존 백업 등의 비용이 남음. RDS는 중지 후 최대 7일이 지나면 자동 시작됨.

재개 시 RDS가 사용 가능 상태가 된 뒤 EC2 시작. 주소가 바뀌었다면 CloudFront API 원본, Django 허용 호스트, GitHub ORIGIN_HOST도 갱신. 탄력적 IP를 유지하면 주소 변경을 줄일 수 있음. EC2 IAM 역할·컨테이너·API 상태를 확인한 후 브라우저 접속.

## 7. 새 환경 검증 후 기존 EC2 삭제

AWS 콘솔에서 **이전 EC2의 인스턴스 ID**를 먼저 확인. 새 EC2와 이름만 보고 구분하지 않음. 필요한 소스·환경 설정·데이터가 별도로 확보되어 있고 새 환경이 정상일 때만 **인스턴스 상태 → 인스턴스 종료(삭제)** 선택.

기존 S3 대화 버킷은 새 앱에서도 사용하므로 삭제하지 않음. 새 EC2로 옮긴 탄력적 IP도 유지. 이전 EC2에만 연결했던 EBS가 남았는지 확인하며, 필요한 백업이나 다른 학생의 자원은 삭제하지 않음.

## 8. 전체 실습을 끝낼 때

아래는 더 이상 서비스를 유지하지 않을 때만 진행. 학생별 이름·ID를 확인하고 본인 실습 자원만 정리.

1. GitHub 저장소의 **Actions → Deploy React and Django → 메뉴 → Disable workflow**로 자동 배포 중단.
2. 도메인을 사용했다면 서비스 www·origin 레코드 정리. 다른 서비스의 DNS·검증 레코드는 유지.
3. CloudFront 배포 **비활성화 → 반영 완료 대기 → 삭제**. 프론트 버킷을 공개해 대신 접속시키지 않음.
4. 생성했던 ALB 삭제 후 연결이 해제된 실습 대상 그룹 정리. EC2 중지만으로 ALB 비용이 사라지지 않음.
5. 필요한 DB 데이터 보관 후 RDS 삭제. 삭제 방지가 켜져 있으면 해제. 최종 스냅샷·자동 백업 보존 여부는 데이터를 다시 쓸지에 따라 선택.
6. 새 EC2 종료 후 남은 EBS 확인. 더 이상 사용하지 않는 탄력적 IP는 연결 해제 후 **릴리스**.
7. 프론트 버킷과 대화 버킷 각각 필요한 파일을 보관한 뒤 **비우기 → 삭제**. 버전 관리가 켜져 있으면 이전 버전·삭제 마커도 확인.
8. ECR의 실습 이미지·저장소, 미사용 CloudFront OAC, 실습용 IAM 역할·정책·보안 그룹·DB 서브넷 그룹 정리. 공유 자원이면 유지.
9. 보존한 RDS 스냅샷·백업·로그와 Bills 사용 항목 확인. 비용 반영에는 시간이 걸릴 수 있음.

**공식 문서:** [EC2 종료](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/how-ec2-instance-termination-works.html), [RDS 중지](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_StopInstance.html), [S3 비우기](https://docs.aws.amazon.com/AmazonS3/latest/userguide/empty-bucket.html).
