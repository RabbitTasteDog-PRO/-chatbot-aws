# 새 EC2 준비와 기존 환경 보관

## 1. 기존 환경 보관

이번 실습은 새 프로젝트 `chatbot_aws`를 사용. 기존 EC2는 새 앱의 배포가 끝날 때까지 중지 상태로 보관하고, 기존 S3 버킷은 대화 TXT 저장용으로 계속 사용.

1. 기존 EC2에만 있는 수정 소스와 필요한 데이터가 있는지 확인.
2. 실제 `.env`와 필요한 데이터는 본인 PC의 비공개 폴더에 보관. GitHub·수업 공유 폴더에는 올리지 않음.
3. AWS 콘솔 **EC2 → 인스턴스 → 기존 인스턴스 선택 → 인스턴스 상태 → 인스턴스 중지** 클릭.
4. 기존 탄력적 IP를 새 EC2에 옮길 경우 **네트워크 및 보안 → 탄력적 IP → 해당 주소 선택 → 작업 → 탄력적 IP 주소 연결 해제**. 새 EC2 생성 후 다시 연결.

**확인 결과:** 기존 EC2의 상태가 `중지됨`. `종료됨`으로 만들지 않음. 중지 상태에도 EBS와 보유한 탄력적 IP의 비용은 남음.

## 2. 새 EC2 생성

콘솔 오른쪽 위 리전을 **아시아 태평양(서울)**로 선택. **EC2 → 인스턴스 → 인스턴스 시작**을 열고 위에서 아래로 입력.

`ALIAS`는 본인의 영문 별칭으로 변경. 같은 AWS 계정을 사용하는 학생끼리 인스턴스·보안 그룹 이름을 구분하기 위한 값임.

| 화면 항목 | 선택·입력값 |
| --- | --- |
| 이름 및 태그 | `skn33-day3-ALIAS` |
| 애플리케이션 및 OS 이미지 | **Ubuntu → Ubuntu Server 24.04 LTS** |
| 아키텍처 | **64비트(x86)** |
| 인스턴스 유형 | `t3.small` 권장. `t3.micro`도 간단한 수업 앱 실행은 가능하지만 메모리 여유가 적음 |
| 키 페어 | 기존 `skn33-aws-key` 선택. 이 키의 `.pem`을 가지고 있는지 확인 |
| 네트워크 설정 → 편집 → VPC | 수업에서 사용하는 기본 VPC 선택. VPC ID 기록 |
| 서브넷 | 위 VPC의 기존 퍼블릭 서브넷 하나. 가용 영역 기록 |
| 퍼블릭 IP 자동 할당 | **활성화** |
| 방화벽 | **보안 그룹 생성** |
| 보안 그룹 이름 | `skn33-day3-ec2-ALIAS` |
| 인바운드 | **SSH / TCP 22 / 내 IP** 한 개 |
| 스토리지 | `gp3`, 20 GiB. 루트 볼륨 하나 |
| 고급 세부 정보 → IAM 인스턴스 프로파일 | [권한 준비](00_권한_준비.md)의 EC2 역할 선택 |

**인스턴스 시작** 클릭. 인스턴스 목록에서 새 인스턴스를 선택하고 **세부 정보**의 인스턴스 ID·퍼블릭 IPv4·퍼블릭 DNS를 기록.

탄력적 IP를 재사용할 경우 **탄력적 IP → 해당 주소 → 작업 → 탄력적 IP 주소 연결 → 인스턴스 → 새 인스턴스 선택 → 연결**. 이후 주소와 DNS는 새 인스턴스 화면에서 다시 복사.

**확인 결과:** 인스턴스가 `실행 중`이고 상태 검사 통과. RDS 생성 시 사용할 VPC ID가 기록되어 있음. HTTP 인바운드는 CloudFront를 준비하는 5단계에서 추가.

## 3. SSH와 Docker 준비

Mac은 기존 SSH 가이드, Windows는 기존 MobaXterm 가이드의 **접속 주소만 새 EC2 주소로 변경**. 사용자 이름은 `ubuntu`, 개인 키는 `skn33-aws-key.pem` 사용.

아래 명령은 **SSH로 접속한 새 EC2 터미널**에서 실행. 먼저 패키지를 준비.

```bash
sudo apt update
sudo apt install -y ca-certificates curl unzip python3-venv
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
```

다음 블록을 첫 줄부터 마지막 줄까지 붙여넣어 Docker 저장소 등록.

```bash
sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: noble
Components: stable
Architectures: amd64
Signed-By: /etc/apt/keyrings/docker.asc
EOF
```

```bash
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker version
sudo docker compose version
```

**확인 결과:** Docker Client·Server 버전과 Compose 버전 출력. `apt`나 `curl`이 대기하면 아래 아웃바운드 표 확인. 기존 1일차 Docker 설치 가이드를 새 EC2에서 완료했다면 이 설치는 생략.

## 4. AWS CLI와 SSM 준비

같은 EC2 터미널에서 AWS CLI 설치. EC2에서는 `aws login`을 하지 않고 인스턴스에 연결한 IAM 역할 사용.

```bash
curl -fL --connect-timeout 10 --max-time 120 https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip -o /tmp/awscliv2.zip
unzip -q /tmp/awscliv2.zip -d /tmp/aws-day3-cli
sudo /tmp/aws-day3-cli/aws/install
aws --version
aws sts get-caller-identity --region ap-northeast-2
```

**확인 결과:** AWS CLI v2와 EC2 역할의 ARN 표시. `Unable to locate credentials`이면 EC2에 IAM 역할이 연결됐는지 확인.

Ubuntu 이미지에 SSM Agent가 있는지 확인.

```bash
sudo snap list amazon-ssm-agent
```

패키지가 없다고 나오면 아래 명령으로 다른 설치 방식도 확인.

```bash
sudo systemctl status amazon-ssm-agent --no-pager
```

서비스가 이미 있으면 해당 서비스를 사용하고 Snap으로 중복 설치하지 않음. Snap·systemd 어느 쪽에도 설치되어 있지 않을 때만 아래 명령 실행.

```bash
sudo snap install amazon-ssm-agent --classic
```

Snap으로 설치된 경우 아래 두 명령 실행. 기존 systemd 방식이면 `sudo systemctl enable --now amazon-ssm-agent` 실행.

```bash
sudo snap start --enable amazon-ssm-agent
sudo snap services amazon-ssm-agent
```

**AWS Systems Manager → 노드 관리 → 플릿 관리자(Fleet Manager)**에서 새 인스턴스가 관리형 노드로 나타나고 연결 상태가 Online인지 확인. 나타나지 않으면 EC2 역할의 `AmazonSSMManagedInstanceCore`와 HTTPS 아웃바운드 확인.

## 5. Docker의 EC2 역할 접근 설정

**내 PC 터미널**에서 진행. Mac은 터미널, Windows는 WSL Ubuntu 터미널을 사용. [권한 준비](00_권한_준비.md)에서 로그인한 `skn33` 프로필 사용. `INSTANCE_ID`를 새 인스턴스 ID로 변경.

```bash
aws ec2 modify-instance-metadata-options --instance-id INSTANCE_ID --http-endpoint enabled --http-tokens required --http-put-response-hop-limit 2 --region ap-northeast-2 --profile skn33
aws ec2 describe-instances --instance-ids INSTANCE_ID --query 'Reservations[0].Instances[0].MetadataOptions' --region ap-northeast-2 --profile skn33
```

**확인 결과:** `HttpTokens: required`, `HttpPutResponseHopLimit: 2`, `State: applied`. `pending`이면 잠시 후 조회. Docker 내부 Boto3가 EC2 역할의 임시 자격 증명을 받기 위한 설정임. 기관 IAM 사용자에게 수정 권한이 없으면 관리자에게 해당 인스턴스만 변경 요청.

## 6. 보안 그룹 연결표

**EC2 → 인스턴스 → 새 인스턴스 → 보안 → 보안 그룹 링크**에서 인바운드·아웃바운드 탭을 구분. EC2가 받는 요청은 인바운드, EC2가 다른 서비스로 보내는 요청은 아웃바운드임.

| 적용 대상 | 방향 | 유형·포트 | 소스 또는 대상 | 적용 시점 |
| --- | --- | --- | --- | --- |
| 새 EC2 보안 그룹 | 인바운드 | SSH 22 | 내 PC 공인 IP `/32` | 지금 |
| 새 EC2 보안 그룹 | 인바운드 | HTTP 80 | CloudFront 관리형 접두사 목록 | 5단계 |
| 새 EC2 보안 그룹 | 아웃바운드 | 기본 모든 트래픽 | `0.0.0.0/0` | 기본 규칙이 있으면 그대로 사용 |
| 새 EC2 보안 그룹 | 아웃바운드, 제한형일 때만 | HTTP 80 / HTTPS 443 | `0.0.0.0/0` | apt·Docker·AWS·외부 API 다운로드 |
| 새 EC2 보안 그룹 | 아웃바운드, 제한형일 때만 | MySQL/Aurora 3306 | RDS 보안 그룹 ID | 2단계 |
| RDS 보안 그룹 | 인바운드 | MySQL/Aurora 3306 | **새 EC2 보안 그룹 ID** | 2단계 |

**기본 아웃바운드 전체 허용이 있으면 제한형 규칙 3개를 중복 추가하지 않음.** 기관에서 아웃바운드를 제한했다면 80·443·3306을 목적에 맞게 추가. RDS 응답을 받기 위해 EC2 인바운드 3306을 열 필요는 없음.
